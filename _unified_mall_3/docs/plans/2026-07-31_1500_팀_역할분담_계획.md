## 0. 원칙 — "층"이 아니라 "이음매"로 자른다

가장 흔한 실패는 **프론트 / 백엔드 / AI 로 나누는 것**이다. 그러면 화면 담당은 API를 기다리고,
API 담당은 스키마를 기다리고, AI 담당은 데이터를 기다린다. **전원이 서로를 기다린다.**

이 프로젝트는 이미 **포트(인터페이스)로 잘려 있다.** 그 경계가 그대로 분담선이다.
각자 "세로로 한 조각"을 끝까지 책임지고, 남과는 **계약(§2)으로만** 만난다.

### 못박을 세 가지

1. **P0는 분담 전에 다 같이 끝낸다.** 스키마 + 합성/실제 물리분리 + 포트 시그니처 확정.
   계약 없이 병렬로 들어가면 만든 것의 절반이 재작업이 된다.
2. **모든 트랙은 첫날부터 fixture로 개발한다.** 남의 산출물을 기다리는 트랙은 없어야 한다.
3. **데이터 취득(B)을 데모의 임계경로에 두지 않는다.** 이용약관·저작권 때문에 막힐 수 있다.
   **B가 0건이어도 데모는 합성 데이터로 완주해야 한다.**

| 범위 | P1 수직슬라이스, P2 규칙엔진 |

## 2. 계약 — 트랙 간 접점은 이것뿐

이 표에 없는 방식으로 남의 코드를 직접 부르지 않는다.

| 계약 | 제공 | 소비 | 형태 |
|---|---|---|---|
| `EvidenceReview` | A | D | `status` + `verification_method`(예: `admin_review`) |
| `CohortStats` | D | E, F | `{n, 분포, data_source, collection_path, warnings[]}` |
| `RetrieverPort` | C | A, E | 인용 + **locator**(어느 조항인지) |
| `TermsManifest` | B | C | `insurer·product·generation·valid_from·valid_to·license` |
| OpenAPI / MCP 스키마 | E | 외부 | 화면 없이 전 루프 |

**계약 변경 규칙**: PR로만 바꾸고 **자기 PR 자기 승인 금지**. 매일 15분 스탠드업에서 공유하는 것은
진척이 아니라 **계약 변경뿐**이다.

## 3. 5명 확정 배치

| | 담당 | 트랙 | 이런 사람에게 |
|---|---|---|---|
| **①** | **판정 코어** | A (P1·P2) | 가장 숙련된 사람. 쪼개면 상태 전이가 모순난다 |
| **②** | **약관 파이프라인** | **B+C** | 꼼꼼하고 법적 확인·문서를 견디는 사람 |
| **③** | **집계·편향** | D (P4·P7) | 통계 감각 + ★**남의 결과를 거부할 수 있는 성격** |
| **④** | **에이전트 인터페이스** + 계약관리 + 감사역 | E (P5) | 스펙 정독을 즐기는 사람 |
| **⑤** | **필수기능·화면** | F (P6) | 프론트·멀티미디어, 삽질 내성 |

### 왜 `E+F`가 아니라 `B+C`를 붙였나

5명 배치의 갈림길은 **어느 둘을 합치느냐**다.

| 후보 | 판단 |
|---|---|
| `E+F` 합치기 | ✗ F는 음성·화상·얼굴2FA·관리자보고서·처방전 OCR UI·판정 화면으로 **이미 한 사람 몫**이다. 여기에 MCP·A2A까지 얹으면 과부하고, 기술 스택도 서버 프로토콜 ↔ WebRTC/프론트로 완전히 다르다 |
| **`B+C` 합치기** | ✅ **"약관이 들어와서 검색되기까지"가 한 덩어리**다. 같은 도메인·같은 데이터·순차 의존(B의 매니페스트 → C가 소비). ★결정적으로 **B가 이용약관·사이트 정책으로 막혀 있는 동안 그 유휴시간을 C가 흡수**한다 |

### 이 배치의 이점 — 관리할 합류점이 2개에서 **1개**로 준다

§4의 합류 지점 중 **B→C가 ②의 머릿속으로 들어가 사라진다.** 일정에서 추적할 것은
**A→D(`verified`가 집계를 실제로 바꾸는 순간) 하나뿐**이다.

### ④에게 겸직을 얹는 이유

E는 구현 부하가 가장 가볍다. 대신 두 가지를 준다.

- **계약 관리자** — P0에서 **OpenAPI/MCP 스키마를 먼저 확정**하고, 나머지 전원이 그 스펙에 맞춰 구현한다.
  E와 F는 남의 결과를 모두 소비하는 위치라 통합이 가장 늦게 터지는데, **계약을 E가 소유하면
  통합이 마지막이 아니라 첫날 일어난다.**
- **정직성 감사역**(§5) — ①(A 담당)은 겸직 대상에서 제외한다.

### 부하 균형은 A를 쪼개서 맞추지 않는다

**①이 가장 무겁고 ④가 가장 가볍다.** 균등하게 만들려고 A를 둘로 나누면 상태 전이가 깨진다.
대신 **발표·산출물 문서·README를 ①에게서 완전히 걷어내 ④에게** 준다.

### ★1주차에 ③이 가장 먼저 내놓아야 하는 것

집계 API가 아니라 **합성 데이터 생성기(P7)** 다. 이게 없으면 ①②④⑤가 fixture 없이 시작하고,
"첫날부터 fixture로 개발한다"(§0-2)는 원칙이 무너진다.
**③은 1주차에 팀 전체의 공급자이고, 그 뒤에 게이트키퍼가 된다.**

### 인원이 바뀌면

| 인원 | 배치 |
|---|---|
| 6명 | ②를 B / C로 분리 |
| 4명 | ④와 ⑤를 합침(E+F) — 과부하를 감수하고 F의 화상·음성 범위를 줄인다 |
| 3명 | A+D / B+C / E+F — ★A와 D가 한 사람에게 가면 **적대적 짝이 사라진다.** 이 경우 `consistent` 레코드를 집계 함수에 넣으면 **테스트가 깨지도록** 먼저 작성해, 사람 대신 테스트가 거부하게 한다 |

## 4. 순서 — 누가 언제 시작하나

```
[전원] P0  스키마 + 합성/실제 물리분리 + 포트 시그니처 확정   ← 여기 끝나야 갈라진다
   │
   ├─ A  P1 수직슬라이스 ──────────→ P2 규칙엔진        (임계경로)
   ├─ B  S5 약관·저작권 확인 ──────→ S7 수집 → 식별
   ├─ C  합성 fixture로 검색 개발 ─→ B 매니페스트 연결
   ├─ D  합성 생성기 + 집계 게이트 → A의 verified 연결
   ├─ E  OpenAPI/MCP 스키마 확정 ─→ 실제 구현 연결
   └─ F  화면 골격 + 필수기능 ────→ 판정 결과 연결
```

**합류 지점 2개**: ①A→D(`verified`가 집계를 실제로 바꾸는 순간) ②B→C(실물 약관 교체).
이 두 지점만 일정에서 관리하면 나머지는 각자 속도로 간다.

## 5. 리뷰 — 자기 트랙을 자기가 "검증"하지 않는다

이 프로젝트에서 **반복해서 나온 실패는 정합성 확인을 "검증"이라고 부른 것**이다
(바운티 L1의 근거성↔사실성 혼동, 보험 Outcome 확정 초안). 사람 배치로 막는다.

- **정직성 감사역 1명 겸직**(A 담당자는 제외): 각 트랙이 "검증했다"고 쓸 때
  **실제로 무엇을 확인했는지** 한 줄로 답하게 한다. 답이 "형식이 맞았다"면 그건 검증이 아니다.
- **A ↔ D**는 구조적으로 적대적이다(§1-D). 이 긴장을 없애지 않는다.
- **F는 매 단계 실제 화면을 연다.** 백엔드 통과를 화면 확인으로 대체하지 않는다.

## 6. 한계 (정직 기록)

- 인원(5명)은 확정이나 **기간과 팀원별 숙련도는 모르는 상태**에서 쓴 설계다.
  §3의 "이런 사람에게" 열은 실제 팀원을 보고 조정해야 한다.
- §4의 주차 구분은 **상대적 순서**이며 실제 마감 일정에 맞춘 것이 아니다.
- 트랙 크기가 균등하지 않다. **A가 가장 무겁고 E가 가장 가볍다.** 균등 분배를 원하면
  A를 쪼갤 게 아니라 **A 담당자에게서 문서·발표를 덜어내는 방식**으로 맞춘다.
- B는 외부 요인(이용약관·사이트 정책)으로 **성과가 0일 수 있다.** 그것이 그 담당자의 실패로
  평가되지 않도록, B의 KPI를 "수집 건수"가 아니라 "확인·식별 절차의 완결성"으로 둔다.
