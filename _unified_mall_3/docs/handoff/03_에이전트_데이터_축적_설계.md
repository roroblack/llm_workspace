# 외부 에이전트 데이터 — 어떻게 받고, 쌓고, 다시 쓰나

전원 참고 · 코덱스 교차검증

---

## 0. 시나리오

사용자의 **에이전트**가 우리 API를 부른다. 그 에이전트는 이미 가진 것이 있다 —
과거 청구 이력, 다른 데서 받은 판정, 실제 지급 결과. 그걸 우리에게 주기도 한다.

우리는 그걸 쌓아서 **승인율**과 **우리 판정의 사후 검증**에 쓰려 한다.

---

## 1. 제1원칙 — **약관과 같은 급으로 쓰지 않는다**

이게 전부다.

> 남의 에이전트가 "이 건 지급됐어요"라고 말했다고 해서,
> 그걸 근거로 다른 사용자에게 **"보장됩니다"라고 말하면 안 된다.**

약관 조항은 **회사가 공시한 계약 내용**이고, 외부 보고는 **주장**이다.
둘을 같은 인덱스에 넣으면 검색에서 섞이고, 섞이면 인용에서 구분할 수 없다.

```python
class EvidenceTier(str, Enum):
    POLICY_CLAUSE   = "policy_clause"     # 약관 원문 — 유일하게 판정 근거가 된다
    EXTERNAL_REPORT = "external_report"   # 외부 보고 — 참고만
    STATISTICS      = "statistics"        # 집계 — 참고만
```

`precheck.run()` 은 `POLICY_CLAUSE` 만 인용한다. 코드로 강제돼 있다.

## 2. 어떤 문서 형태로 저장하나 — **원본 그대로 + 이벤트 로그**

### 2-1. 받은 것은 손대지 않고 남긴다

```
data/external/submissions/{YYYY-MM}/{client_ref}/{received_at}_{idem_key}.json
```

```json
{
  "received_at": "2026-08-02T14:03:11Z",
  "client_ref": "agent-abc",
  "idempotency_key": "…",
  "payload": { "…클라이언트가 보낸 그대로…" },
  "signature": { "api_key_id": "…", "ip_hash": "…" }
}
```

**왜 원본을 남기나** — 나중에 파싱 규칙이 바뀐다. 정규화한 것만 두면
"그때 뭘 받았나"를 다시 볼 수 없다. 약관 PDF를 원본으로 두는 것과 같은 이유다.

### 2-2. 정규화한 것은 이벤트 로그로

```
data/external/events/{YYYY-MM-DD}.jsonl     (append-only)
```

```json
{"event":"claim_outcome","at":"…","client_ref":"agent-abc",
 "insurer":"DB손해보험","enrolled_on":"20200301","kcd_codes":["F32"],
 "outcome":"denied","verification":"unverified","precheck_trace_id":"744154ed…"}
```

**추가만 한다(append-only).** 수정·삭제하지 않는다 — 통계가 조용히 바뀌면 안 된다.
정정이 필요하면 정정 이벤트를 **뒤에 붙인다.**

## 3. DB에는 어떻게

| 테이블 | 역할 |
|---|---|
| `external_submission` | 원본 `payload jsonb` + `idempotency_key` UNIQUE |
| `claim_outcome` | 정규화된 결과 1행 |
| `evidence_verification` | 검증 이력 (누가·언제·무엇으로) |

### 검증 등급

```
unverified       받기만 했다. 기본값. ★통계에 넣지 않는다
self_reported    본인이 신고했고 신원은 확인됐다
document_backed  지급명세서 등 문서가 붙었다
confirmed        보험사 확인 또는 교차검증 통과
```

**`unverified` 를 승인율에 넣으면 안 된다.**
넣으면 "우리 서비스로 청구하면 90% 나옵니다" 같은 수치가 근거 없이 만들어진다.

## 4. 다시 쓰는 형식 — 세 가지, 각각 다른 급

### 4-1. 승인율 통계 (사용자에게 보여 줌)

```
"이 보험사의 F32 청구 33건 중 지급 26건 (검증된 건만)"
```

조건:
- `verification >= document_backed` 인 것만
- **표본이 작으면 숫자를 보여 주지 않는다** — `n < 30` 이면 "사례가 적습니다"
- 반드시 "실제 결과는 다를 수 있습니다" 를 함께 낸다

### 4-2. 우리 판정의 사후 검증 (내부용)

`precheck_trace_id` 가 붙어 온 보고는 **우리 답과 대조**할 수 있다.

```
우리 판정         실제 결과      해석
not_covered   →  denied        맞았다
not_covered   →  paid          ★틀렸다. 조항 해석을 다시 봐야 한다
unknown       →  paid          기권했지만 실제로는 보장됐다. 검색 보강 필요
```

이게 **가장 값어치 있는 쓰임**이다. 정확도를 숫자로 잴 수 있게 된다.

### 4-3. 검색 평가 세트 (모델팀용)

실제 사례를 골든 세트로 만든다. **판정에 직접 쓰지 않는다.**

## 5. ★어떤 RAG 형태가 되나 — **인덱스를 분리한다**

```
인덱스 A  약관 조항        canonical_clause.embedding
          → 판정 근거로 인용된다
          → 필터: policy_version_id 로 **반드시** 가둔다

인덱스 B  외부 사례        external_case.embedding
          → 인용되지 않는다. "비슷한 사례가 있습니다" 로만 쓴다
          → 필터: verification 등급
```

### 왜 합치면 안 되나

1. **인용이 섞인다.** 답변에 "제9조에 따르면"과 "어떤 사용자 보고에 따르면"이
   같은 출처 목록에 나란히 붙으면 사용자는 구분하지 못한다.
2. **검색 순위가 오염된다.** 사례 문장은 구어체라 사용자 질문과 더 비슷하다.
   같은 인덱스에 두면 **약관 조항을 밀어낸다.**
3. **약관은 버전으로 가둬야 한다.** 사례에는 그런 축이 없다.

### 검색 흐름

```
질문
 ├─ 인덱스 A 검색 (policy_version_id 고정)  → 판정 근거
 └─ 인덱스 B 검색 (선택)                     → "비슷한 사례" 참고 표시

답변 = 판정(A 근거만 인용) + 참고(B, 별도 구역에 "참고 사례"로 표시)
```

**두 구역을 화면에서도 나눈다.** 근거와 참고가 같은 목록에 있으면 안 된다.

## 6. 인증·감사

| 항목 | 방침 |
|---|---|
| 인증 | 클라이언트별 API 키(해시 저장) + scope. 외부 공개 시 OAuth 2.1 |
| scope | `precheck:read` `terms:read` `observations:write` `cohort:read` |
| 멱등성 | 쓰기 요청에 `Idempotency-Key` **필수** |
| 레이트리밋 | `client_id + subject_hash + operation` 기준 |
| 감사로그 | **원문 의료정보 대신 해시.** client, policy_version, clause_ids, rule/model version, verdict, abstain 사유, latency |
| 보존 | 원문 payload는 암호화·별도 보존기간·삭제 가능 |

질병기호는 민감정보다. 로그에 그대로 남기지 않는다.

## 7. 4주 안에 할 것 / 미룰 것

| 할 것 | 미룰 것 |
|---|---|
| `POST /v1/observations` 접수 + 원본 저장 | 자동 검증 파이프라인 |
| `verification=unverified` 로 쌓기 | 사용자향 승인율 노출 |
| `precheck_trace_id` 대조 리포트(내부) | 사례 임베딩·인덱스 B |
| 감사로그 | OAuth 2.1 |

**승인율을 사용자에게 보여 주는 것은 검증된 데이터가 쌓인 뒤다.**
지금 보여 주면 근거 없는 숫자가 된다.
