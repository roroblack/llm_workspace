2. 설계의 뼈대 세 가지

① 조항의 내용과 수록을 나눈다

실측: 조항 12,534개 중 서로 다른 내용은 4,860개. 75%가 중복이고 한 조항이 최대 73개 문서에 실린다.
테이블역할
canonical_clause내용이 정체성(content_hash PK). 본문·임베딩을 한 번만 저장
clause_occurrence어느 문서 어느 쪽에 실렸나. 인용은 반드시 이쪽을 가리킨다

임베딩을 중복째 넣으면 비용·인덱스가 4배가 되고 검색 결과가 같은 내용으로 도배된다. 그러나 인용은 "2019년 약관 41쪽"이라고 정확히 대야 한다. 그래서 나눈다.

② 날짜는 노드가 아니라 관계에 붙는다

[조항 내용 abc…]  "제9조 지급보험금의 계산"
      ↑ 수록 (2015-01-01 ~ 2017-03-31)
      ↑ 수록 (2017-04-01 ~ 2021-06-30)      ← 날짜는 여기
[약관 문서]

조문이 개정되면 내용이 달라져 해시가 달라진다 → 자동으로 다른 노드가 된다. 개정 이력이 저절로 보존된다.

③ 외부에서 온 것은 급을 나눈다

남의 에이전트가 "이 건 지급됐어요"라고 한 것을 근거로 "보장됩니다"라고 말하면 안 된다. 약관 조항은 회사가 공시한 계약 내용이고, 외부 보고는 주장이다. 같은 인덱스에 넣으면 검색에서 섞이고, 섞이면 인용에서 구분할 수 없다.

6. 준용 순회 — 반드시 버전 안에 가둔다

실측: 조항 간 상호참조 72,099개(표본 400문서). 그중 2/3이 문서 밖을 가리킨다. 
제1조(자기부담금) 회사는 보통약관에서 정한 손해가 발생하는 경우 손해액에서
1사고당 (     )을 빼고 보통약관 제9조(지급보험금의 계산)에 따라 보상합니다.

이 특약만 읽으면 자기부담금을 알 수 없다. 괄호가 비어 있다.

WITH RECURSIVE walk(occ_id, depth) AS (
    SELECT id, 0 FROM clause_occurrence WHERE id = $1
  UNION ALL
    SELECT r.target_occurrence_id, w.depth + 1
    FROM walk w
    JOIN clause_reference r ON r.src_occurrence_id = w.occ_id
    JOIN clause_occurrence o ON o.id = r.target_occurrence_id
    JOIN policy_document d   ON d.id = o.document_id
    WHERE w.depth < 3
      AND d.policy_version_id = $2   -- ★같은 약관 버전 안에서만
)

policy_version_id로 묶지 않으면 2019년 약관을 보다가 2024년 조항으로 넘어간다.

7. 왜 별도 그래프DB를 쓰지 않나

조건해당?
깊이를 모르는 순회✅ 준용 사슬이 몇 단인지 모른다
경로 자체가 답✅ "왜 면책인가"를 조항 경로로 설명한다
스키마가 자주 바뀜❌ 약관 구조는 안정적이다
수억 엣지❌ 약 30만이다

앞의 둘은 Postgres 재귀 CTE로 된다. 그리고 pgvector와 갈라지면 "유사 조항 + 그 조항이 준용하는 조항"을 한 번에 조인할 수 없다.

8. API 계약

엔드포인트역할
POST /v1/prechecks보장 사전판정
GET /v1/support-manifest무엇을 지원하는지
POST /v1/observations외부 에이전트의 청구 결과 보고
HTTP 상태 코드 — 이 구분이 무너지면 안 된다
  • 200 — 판정했다. verdict="unknown"이어도 200이다
  • 422 — 입력이 잘못됐다(가입일 형식 등)
  • 503 — 검색·DB 장애. 이때만 우리 잘못이다
기권을 503으로 내보내면 클라이언트가 "근거 없음"과 "서버 장애"를 못 가린다.
