- 작성: 2026-08-01
- 수집 대상: **실손의료보험 약관 PDF** (진료비 내역서 KCD × 약관 → 보장 사전검토에 쓸 근거)
- 결과: **12개사 1,817건 / 5.16GB**

## 0. 무엇을 요청받았고 무엇을 모았나

프로젝트 목표는 "진료비 내역서의 질병기호(KCD) + **실손보험 약관** → 보장 여부 사전검토"다.
따라서 모아야 할 것은 **실손의료보험의 보험약관 PDF**다.

수집 정책으로 세 가지를 정했고 끝까지 지켰다.

| 정책 | 이유 |
|---|---|
| **약관만** 받는다 | 요약서·사업방법서는 판정 근거로 인용할 수 없다 |
| **실손만** 받는다 | 다른 보종은 이 프로젝트의 판정 대상이 아니다 |
| **판매중지분도** 받는다 | 사용자의 계약은 과거 세대일 수 있다. 현재 판매분만으로는 판정이 안 된다 |

## 2. "결과가 좋다"는 근거 — 검증 5종

주장만으로는 부족하므로 **측정한 것만** 적는다.

### ① 받은 것이 약관인가 — 표본 검증

12개사에서 각 6건씩 무작위로 뽑아 **1쪽 표지 텍스트**를 읽었다.

- **요약서·사업방법서로 잘못 받은 것: 0건**
- '기타'로 분류된 것들은 표지가 비었거나 바로 `보통약관 제1조`로 시작하는 것들이었다
  (예: KB `LIG개인실손의료비보험 보통약관 …제1장 일반사항`)
- **쪽수 중앙값 120~299쪽** — 요약서(4쪽)·사업방법서(1쪽)와 확연히 다르다

### ② 파일이 온전한가 — 전수 검사

**1,817건 전부**에 대해 `%PDF` 시작 + 꼬리 `%%EOF` 를 확인했다.

- **잘린 파일 0개**
- 검사 도입 전에는 **165개가 잘려 있었다**(§3-② 참조). 지금은 없다.

### ③ 실손만 남았는가 — 전수 분류

파일명·상품명·카탈로그 조인으로 전수 확인했다.

- **비실손 0건**
- 삼성화재 79건·DB손보 61건이 처음에 "비실손"으로 잡혔으나 **카탈로그와 조인하니 전부 실손**이었다
  (파일명이 `약관_30565(16)_20260701` 처럼 코드만 있어 생긴 오탐)
- 삼성생명 **443건은 진짜 비실손**이었고 삭제했다(§3-④)

### ④ 판매중지분이 들어 있는가

과거 세대 약관이 없으면 판정이 안 된다. 실제로 들어 있다.

| 현대해상 | 261 / 307 (85%) |

### ⑤ 개정 이력이 있는가

같은 상품의 판매기간별 개정판이 필요하다(계약 시점에 맞는 약관을 골라야 하므로).

|---|---|---|
| "롯데손보는 방화벽 차단이라 불가" | **접근 가능.** 브라우저 자동화만 걸렸고 URL 도 404 였다 | 파이썬으로 직접 요청해 보니 200 |

## 4. 도중에 잡은 사고 4건 (전부 "정상으로 보였던" 것들)

### ① 매니페스트 유실 — 388개 중 377개가 기록 없음

디스크가 100% 차자 **PDF 는 써지고 매니페스트 append 만 실패**했다.
그 결과 식별 파이프라인이 **28건만** 보고 있었다.

→ 파일명 `{sha12}_{원본}` 이 카탈로그와 조인돼 **377개 전부 복구**(미매칭 0, 재다운로드 0).
   식별 대상 28 → 302건.

### ② 잘린 PDF 165개 — 매직바이트를 통과했다

정확히 **65,536B(64KB 버퍼 하나)** 짜리 파일들이 `[OK]` 로 저장됐다.
`%PDF` 로 시작해 검사를 통과했지만 **열면 0쪽**이었다.

원인이 세 겹이었다.

1. **응답을 끝나기 전에 읽음** — `resp.body()` 를 스트리밍 중 호출 → `resp.finished()` 추가
2. **팝업을 너무 빨리 닫음** — 2.5초 → 9초
3. **프로세스 12개가 동시 실행** — `pkill` 이 Windows 에서 안 먹어 옛 코드가 계속 살아 있었다

→ 방어로 **꼬리 `%%EOF` 검사**를 넣었다. 재실행 후 **잘린 파일 0개**.

### ③ 중복 기록 — 한 sha 가 38번

배치 끝에 몰아 쓰다 중간에 죽으면 기록이 날아가고, 재시작하면 또 쌓였다.
기록이 **9,574행**까지 부풀었다(실제 파일 2,260개).

→ 한 건마다 **즉시 기록** + **sha 기준 중복 방지** + `supervise.sh` 에 **락**(중복 실행 방지).

### ④ 비실손 443건 — 검색을 못 찾아 전수 조사한 결과

삼성생명에서 연금저축·치아보험·종신보험·퇴직연금까지 받았다.
`input[type='text']` 로 잡아 **숨겨진 통합검색창**을 물었고, fill 이 실패하자
"검색을 쓰지 않는다"고 결론 내려 전체 6,561건을 훑고 있었다.

→ **443건 삭제(1.60GB 확보).** 실제 검색창 `#keywordSearch` 로 실손 **223건**만 받도록 고쳤다.
   전수 조사는 남의 서버에 **30배 부하**를 주는 일이었다.

## 5. 아직 안 끝난 것 (정직 기록)

| 항목 | 상태 |
|---|---|
| **삼성생명** | 실손 **223건 중 52건**. 나머지 수집 중 |
| **한화손해보험** | robots 금지로 제외. 사람이 운영자에게 문의할 사안 |
| **흥국생명 robots** | Fasoo DRM 으로 암호화되어 **읽을 수 없다**. `--robots-confirmed` 게이트로 막아 둠 |
| **커버리지 검증** | 각 사가 공시한 실손 총건수와 우리 수집분을 **대조하지 않았다** |
| **중복 약관** | 같은 상품의 개정판이 많은데 **버전 간 중복 제거를 아직 안 했다** |

### 커버리지를 확인하지 않았다는 것의 의미

"1,817건을 받았다"는 사실이지만 **"받아야 할 것을 다 받았다"는 증명은 아니다.**
사이트가 공시한 실손 총건수를 세어 우리 수집분과 맞춰 봐야 한다.
지금 근거로 말할 수 있는 것은 **"받은 것은 전부 실손 약관이고 온전하다"** 까지다.

## 6. 수집 정책 준수 기록

| 원칙 | 지킨 방법 |
|---|---|
| robots 존중 | 사이트마다 확인. 공시실이 별도 도메인이면 **그 도메인의** robots 를 다시 봄(동양생명) |
| 우회하지 않음 | 헤드리스 탐지·WAF 우회는 하지 않음. 한화손보는 금지 확인 후 제외 |
| 판단 불가 시 사람에게 | 흥국생명 robots 가 DRM 암호화 → 기본 중단, `--robots-confirmed` 로만 진행 |
| 서버 부하 | 요청 간 0.5~1.2초 대기. 파일 상한 60MB |
| 신원 밝힘 | User-Agent 에 `BarobomResearchBot` + 연락처 자리 명시 |
| 원문 미커밋 | 약관은 저작물 — `.gitignore` 로 저장소에 넣지 않음 |
| 모르는 것을 지어내지 않음 | 브라우저 수집분은 URL 을 모르므로 `url=""` + `url_unknown=true` |
