## 1. 구현 결과 요약

기존 ReAct·RAG·A2A·LangGraph·MCP 통합 기능을 유지하면서 다음 기능을 추가했다.

1. 교환·환불·반품 실행 문의를 담당 부서 MySQL 테이블에 저장
2. 웹 UI를 4개 기능 탭으로 개편
3. 긴 텍스트를 map-reduce 방식으로 요약하는 보고서 기능 추가
4. 월간 매출 CSV를 집계하는 임원용 매출 보고서 기능 추가
5. 생성된 보고서를 UTF-8 마크다운 파일로 저장하고 다운로드하도록 구현
6. 실행 확인용 `print()`를 구조적 logger 호출로 변경

## 2. 고객 문의 담당 부서 연계

### 2.1 실행성 문의 판별

`app/services/complaint_service.py`를 새로 추가했다.

- 교환·환불·반품 키워드와 `해 주세요`, `신청`, `접수`, `원합니다` 같은 실행 표현을 함께 검사한다.
- `환불 절차 알려 주세요`, `교환 정책이 뭐예요` 같은 정보성 질문은 DB에 저장하지 않는다.
- 실행성 문의는 일반 LLM·RAG 처리보다 먼저 감지한다.
- 메인 `/api/v1/chat`과 전용 `/api/v1/complaints/connect`에서 동일한 판별 로직을 사용한다.

실행 문의가 확인되면 사용자에게 다음 문구를 정확히 반환한다.

```text
담당 부서로 연결해 드리겠습니다.
```

### 2.2 담당 부서 자동 배정

화면에서 `dept_id`를 직접 지정하지 않은 경우 문의 내용으로 담당 부서를 결정한다.

| 문의 유형 | 자동 배정 dept_id |
|---|---|
| 교환 | `CS_EXCHANGE` |
| 환불 | `CS_REFUND` |
| 반품 | `CS_RETURN` |
| 기타 | `CS_GENERAL` |

### 2.3 MySQL 저장 구조

대상 데이터베이스는 `fastapi_db`, 테이블은 `customer_complaint`이다.

| 컬럼 | 구현 타입 | 초기값/용도 |
|---|---|---|
| `cc_id` | BIGINT UNSIGNED, PK, AUTO_INCREMENT | 문의 구분 아이디 |
| `custum_id` | VARCHAR(100) | 과제 명세의 컬럼명을 그대로 사용 |
| `dept_id` | VARCHAR(50) | 담당 부서 아이디 |
| `message` | TEXT | 고객 문의 원문 |
| `receipt_status` | TINYINT(1) | 최초 저장 시 0 |
| `resolution_status` | TINYINT(1) | 최초 저장 시 0 |
| `inquiry_date` | DATETIME(6) | 문의 저장 시각 |
| `receipt_date` | DATETIME(6), NULL | 최초 저장 시 NULL |
| `resolution_date` | DATETIME(6), NULL | 최초 저장 시 NULL |

`mysql_init.sql`을 추가했으며, 애플리케이션에서도 테이블 존재 여부를 확인하고 자동 생성한다. 기존 데이터베이스에 먼저 연결하므로 제한된 운영 계정에 불필요하게 데이터베이스 생성 권한을 요구하지 않는다. `fastapi_db`가 없을 때만 데이터베이스 자동 생성을 시도한다.

MySQL INSERT 실패 시 성공한 것처럼 응답하지 않고 HTTP 503 오류와 원인을 반환하도록 구성했다.

## 3. 웹 UI 탭 개편

`app/templates/index.html`, `app/static/app.js`, `app/static/style.css`를 개편했다.

### 3.1 RAG-TOOL-MEMORY 통합

- 기존 통합 채팅 기능 유지
- OpenAI/Gemini 공급자 선택 유지
- Thread ID 기반 메모리 유지
- LangGraph 실행 trace 표시
- 메인 채팅에 실행성 교환·환불 요청이 입력돼도 담당 부서 저장 흐름으로 우선 연결

### 3.2 문의 처리 연계 부서 연결

- 고객아이디 입력
- 담당 부서 직접 지정 또는 자동 배정
- 문의 내용 입력
- MySQL 저장 결과 표시
- `cc_id`, 담당 부서, 문의 시각, 접수·처리 상태 표시

### 3.3 요약 보고서 만들기

- 보고서 제목과 긴 원문 입력
- 긴 원문을 청크로 분할
- 각 청크 요약(map) 후 부분 요약 통합(reduce)
- `핵심 요약`, `주요 내용`, `후속 조치` 구조로 생성
- 결과를 `reports/summary_*.md`로 저장
- 브라우저 다운로드 링크 제공
- API 키 또는 네트워크 오류 시 원문 문장만 사용하는 안전한 추출 요약으로 대체

### 3.4 임원용 매출 보고서 만들기

- `data/monthly_sales.csv` 사용
- 대상 월과 전월 총매출 비교
- 전월 대비 증감률을 Python 코드로 계산
- 카테고리 매출 1위와 2위 계산
- LLM에는 계산된 확정 수치만 전달
- `총평`, `카테고리 분석`, `다음 달 제언` 구조로 생성
- 결과를 `reports/executive_sales_*.md`로 저장
- API 키 또는 네트워크 오류 시 확정 수치 기반 템플릿으로 대체

## 4. 추가·변경 API

| 메서드 | 경로 | 기능 |
|---|---|---|
| POST | `/api/v1/chat` | 기존 통합 처리 및 실행성 문의 우선 저장 |
| POST | `/api/v1/complaints/connect` | 담당 부서 문의 전용 저장 |
| POST | `/api/v1/reports/summary` | 요약 보고서 생성 |
| POST | `/api/v1/reports/sales` | 임원용 월간 매출 보고서 생성 |
| GET | `/api/v1/reports/{filename}` | 생성 보고서 다운로드 |

보고서 다운로드 경로는 파일명만 허용하고 `reports` 폴더 밖으로 이동하는 경로는 거부하도록 검증한다.

## 5. 설정 및 의존성 변경

### 5.1 `.env.example`

다음 MySQL 설정을 추가했다.

```env
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=root
MYSQL_PASSWORD=
MYSQL_DATABASE=fastapi_db
MYSQL_CONNECT_TIMEOUT=5
```

운영체제의 범용 `DEBUG` 환경변수와 충돌하지 않도록 애플리케이션 디버그 설정은 `APP_DEBUG`를 사용하도록 변경했다.

### 5.2 `requirements.txt`

MySQL 연결을 위해 다음 의존성을 추가했다.

```text
PyMySQL>=1.1,<2.0
```

## 6. 로깅 변경

`app` 및 실행 파일 범위에서 `print()` 호출을 검색해 모두 제거했다.

`app/core/common.py`의 직접 실행 진단 출력은 `setup_logging()`으로 만든 공용 JSON logger를 사용하도록 변경했다. 고객 문의 저장 성공·실패와 보고서 생성·LLM 폴백도 logger에 기록한다.

## 9. 실행 전 확인 사항

현재 프로젝트에는 `.env`가 없으며 로컬 MySQL의 `root` 무암호 접속은 인증 거부됐다. 실제 DB 연계 실행 전 다음 작업이 필요하다.

1. `.env.example`을 `.env`로 복사
2. 실제 `MYSQL_USER`, `MYSQL_PASSWORD` 입력
3. 해당 계정에 `fastapi_db` 접속 및 테이블 생성·INSERT 권한 부여
4. 데이터베이스 생성 권한이 없으면 다음 명령으로 초기화 SQL 선실행

```bash
mysql -u root -p < mysql_init.sql
```

이는 애플리케이션 코드 오류가 아니라 실행 환경 인증 정보가 제공되지 않은 상태다. 인증 정보를 설정하면 전용 문의 탭과 `/api/v1/chat`의 실행성 문의 흐름에서 실제 INSERT가 수행된다.
