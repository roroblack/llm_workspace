# 디버그 노트 — 로컬 Gemma 서버 구동 트러블슈팅

- 일시: 2026-07-12 22:30
- 목적: Phase 3 착수 전, 빌드용 로컬 Gemma(외부 토큰 0)를 실제 구동
- 결과: **성공** — 앱 OpenAI 클라이언트로 정상 한국어 응답 확인

## 겪은 문제와 해결 (시간순)

### 1) llama_cpp.server 의존성 충돌 (해결: 자체 서버 작성)
- `python -m llama_cpp.server` 실행 시 `ModuleNotFoundError: sse_starlette` → 설치
- 이어서 `starlette_context` 요구 → 설치하면 starlette 1.3.1이 딸려와 **fastapi 0.116.1(starlette<0.48)과 충돌**
- sse-starlette 최신은 starlette≥0.49 요구 → fastapi와 양립 불가
- **근본 해결**: `llama_cpp.server`를 버리고, `llama_cpp.Llama`를 직접 감싼 최소 OpenAI 호환 서버를 작성 → `scripts/local_model_server.py`. `create_chat_completion`이 이미 OpenAI 형식을 반환하므로 얇은 패스스루로 충분. 앱과 동일 base 환경(starlette 0.47)에서 충돌 없음.
- 잔여 정리: sse-starlette==2.1.3(호환)만 남김. starlette 0.47.3 유지. 앱 pytest 32개 회귀 없음 확인.

### 2) 모델 로드 실패 → 알고 보니 메모리 부족
- 초기 오류: `Failed to load model from file` (제네릭)
- verbose 로드로 실제 원인 확인:
  - 아키텍처 `gemma4`는 번들 llama.cpp가 **지원함**(kv cache·백엔드까지 진행)
  - 실제 실패: `ggml_backend_cpu_buffer_type_alloc_buffer: failed to allocate buffer of size 552601600` → **컴퓨트 버퍼 할당 실패**
- 원인: 이 머신 **총 16GB, 여유 ~5GB**. 모델 q4_0 = **5.1GB**. 가중치+KV캐시+컴퓨트버퍼가 여유 RAM 초과.

### 3) 메모리 튜닝 (해결)
- 컴퓨트 버퍼는 배치 크기에, KV 캐시는 n_ctx에 비례
- **n_batch=32, n_ubatch=32, n_ctx=1024, use_mmap=True** → 로드 14초 + 추론 성공
- n_ctx=2048은 KV 캐시가 커서 다시 실패 → **n_ctx=1024로 확정**
- 포트 8000을 점유하던 오래된 python 프로세스(다른 세션) 발견 → 정리

## 최종 동작 구성

```
서버:  python scripts/local_model_server.py
       (n_ctx=1024, n_batch=32, use_mmap, http://127.0.0.1:8000/v1)
앱:    LLM_PROVIDER=local → OpenAI SDK(base_url=8000/v1) → Gemma
검증:  "주문 상태를 묻는 고객에게 한 문장으로 응대" →
       "주문하신 상품의 현재 상태를 확인해 드릴게요. 잠시만 기다려 주세요."
```

## Phase 3 이후 주의사항 (중요)
- **로컬 Gemma는 CPU 추론이라 느림**(요청당 수~수십 초). ReAct 다단계 루프는 매우 느릴 수 있음 → max_steps 작게(2~3).
- **Gemma는 OpenAI tool-calling 포맷을 네이티브 지원하지 않을 수 있음** → ReAct 로직 검증은 **결정론적 mock LLM 단위테스트**로 하고(토큰·RAM 무관, CI 포함), 로컬 Gemma 실호출은 `@pytest.mark.llm`로 분리된 수동 스모크로 둔다.
- 서버는 필요할 때만 기동(5GB 상주). 미사용 시 종료로 RAM 회수.
- 운영 환경 RAM 여유 확보 필요. 여유<5.5GB면 로드 실패 가능.
