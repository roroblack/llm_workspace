### Phase 3 — 도구 계층 + ReAct 에이전트 (원리: 수동 루프)
**범위**: react/agent_loop/function_calling/tool_system 흡수
1. `tools/` — DB 기반 커머스 도구 5종+ (재고/가격/주문상태/상품검색/환율)
   - **좋은 도구 5원칙 적용**(PDF6): 한 가지 일 / 이름=기능 / 명확한 인자 / 구체적 독스트링(=모델 프롬프트) / 일관된 반환. 유사 도구는 입력형태·건수·부정조건으로 구분.
   - **도구 실행 오류 처리**(PDF6): 각 도구 `try/except`로 예외를 **구조화된 실패 관찰**(`{"ok": false, "error_code", "message"}`)로 변환해 에이전트가 멈추지 않게 함 (§6 — 정상 결과로 위장 금지)
2. `agent/react.py` — 수동 ReAct 루프 (max_steps, 중복호출 서명 차단, history 트리밍 head+tail, 토큰 추적). **키 부재 시 안내문자열 반환 제거 → ConfigError** (§7)
3. **자동 vs 수동 Function Calling 대비**(PDF6): 모델은 결정(JSON)·실행은 파이썬 원리를 수동 루프로 학습
4. `/api/agent/chat` + 단계 로그(thought/action/observation) + `stopped_by` 반환
- **DoD**: 복합 질문("A상품 재고와 주문상태") 도구 2개 이상 연쇄 호출 로그 + max_steps/중복차단 단위 테스트 + 도구 예외 발생 시 에이전트 미중단 테스트

### Phase 3.5 — LangChain 자동화 계층 (강의 후반 핵심, 신규)
**범위**: langchain_test + PDF5 8강 "원리를 배웠으니 LangChain으로 자동화" 흡수
**YAGNI 원칙(Codex 2차 리뷰 반영)**: 수동 ReAct(Phase 3)와 LangChain(Phase 3.5)을 **둘 다 영구 제품 경로로 유지하지 않는다.** 수동 루프는 **학습·비교용 기준(baseline)**으로 1회 대조 리포트를 남긴 뒤 동결하고, **운영 경로는 LangChain 하나로 수렴**한다. (강의 의도 = 원리를 손으로 구현 후 프레임워크로 자동화)
1. `agent/lc_tools.py` — 커머스 도구를 LangChain `@tool`로 재정의 (Phase 3 도구와 동일 소스 재사용, 중복 구현 금지)
2. `core/llm_clients.py`에 **`get_chat(provider=...)`** LangChain 모델 추상화 통합(OpenAI/Gemini)
3. `agent/lc_agent.py` — `create_agent(llm, tools, system_prompt)` 기반 자동 ReAct → **이후 `/api/agent/chat` 운영 경로로 채택**
4. `agent/planning.py`의 `with_structured_output(Plan)`를 이 계층과 연결
- **의존성**: `langchain`, `langchain-openai`, `langchain-google-genai`, `langgraph`, `pydantic`
- **DoD**: 동일 질문을 수동 루프 vs LangChain 자동으로 1회 대조한 비교 리포트 + 이후 운영 경로가 LangChain으로 단일화됐음을 코드로 확인

### Phase 4 — 프롬프트·Planning 모듈
**범위**: prompt/cot/planning 콘솔 흡수
1. `prompts/` — 역할(역할·태도·안전장치 3요소), few-shot 분류, 인젝션 방어(구분자 `<<< >>>`+심층방어), CoT+자기검증
   - **JSON 강제 3방식 구분 명시**(PDF5): ① 프롬프트 유도 ② `response_mime_type="application/json"` ③ `response_schema`(Pydantic). 스키마 검증 실패 시 재시도(폴백 아님 §6)
   - **CoT 사용/미사용 판단**(PDF6): 단순 질문·함정 문제에서는 CoT를 끄는 조건 명시
2. `ml_eval/` **오분류 개선 루프**(PDF5 신규): CS 문의 60건 분류 → 정확도 측정 → **혼동쌍 집계(Counter)** → 약한 경계에 few-shot 보강 → **재측정** (측정→분석→처방→재측정 순환)
3. `agent/planning.py` — Pydantic Plan + 검증→재계획(max_replan), 에이전트 연동
- **DoD**: 분류 정확도 리포트(예측 vs 정답, **혼동쌍 표**, few-shot 보강 전/후 정확도 비교) + 계획 생성→검증→재계획 로그

### Phase 5 — RAG·문서 처리
**범위**: vector_db/langchain_test/react vector 흡수

- **DoD**: 정책 문서 질문 → 근거 문서(출처 파일명+page) 인용 답변 검증 + 인덱스 저장→재로드 동일결과 테스트 + 거리점수 정렬 방향 단위 테스트

## 6. 에러 처리 taxonomy (신규 — "폴백 금지"와 실무 조화)

RULE 3.2 "폴백 금지"는 **오류를 삼켜 그럴듯한 가짜 결과로 대체하는 것**을 금지하는 것이지, 오류를 사용자에게 알리는 것을 금지하지 않는다. 다음으로 구분한다.

| 상황 | 잘못된 폴백 (금지) | 올바른 처리 (채택) |
|---|---|---|
| API 키 없음 | 데모 응답/안내문자열을 정상 응답처럼 반환 | `ConfigError` → 503 + 명확 메시지 |
| DB 연결 실패 | 빈 리스트 반환 | `InfraError` → 503 |
| LLM이 잘못된 JSON 반환 | 임의 기본 dict로 대체 | 스키마 검증 실패 → **재시도(제한)** 후 실패 시 `LLMOutputError` → 502 |
| 도구 실행 예외 | 조용히 무시하거나 정상 결과처럼 위장 | **구조화된 실패 관찰**(`{"ok": false, "error_code": ..., "message": ...}`)을 모델에 반환(에이전트 학습 의도). 정상 결과 형태로 위장하면 폴백 위반 |
| 사용자 입력 오류 | — | `ValidationError` → 422 |

- `app/core/errors.py`에 예외 클래스와 FastAPI `exception_handler` 정의, 전 라우터 공통 적용.
- **재시도는 폴백이 아니다**: 같은 요청을 정해진 횟수만 재시도하되, 최종 실패는 숨기지 않고 오류로 노출한다.
