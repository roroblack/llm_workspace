## 6. Codex 라운드4 (`reports/_codex_final_acceptance_review_r4.txt`) → 근본 반영
R4 판정: **인수 보류** — 앵커만으론 부족(중간): 비-AppError 예외 메시지가 사용자 인자를 선두에 포함해
`[APPERR:config_error]...`로 시작하면 여전히 조작 가능(문자열 채널은 근본적으로 위조 가능).
→ **위조 불가능한 nonce 도입**(Codex 제안 "고정 표식"의 정확한 구현):
- 클라이언트가 서브프로세스 기동 시 1회용 비밀 `MCP_APPERR_NONCE`(secrets.token_hex(16))를 env로 전달.
- 서버 `_encode_apperr`는 nonce가 있을 때만 `[APPERR:<nonce>:<code>]`로 마커를 싣는다(없으면 원본 전파).
- 클라이언트 `_APPERR_RE`는 **정확한 nonce**를 가진 마커만 신뢰. 호출자 입력은 nonce를 재현할 수 없어
  도구명/인자에 `[APPERR:..]`를 심어도(또는 틀린 nonce) 조작 불가 → InfraError로 안전 처리.
- 테스트: 주입(nonce 없음/틀린 nonce)이 ConfigError로 조작되지 않고 InfraError·ValidationErr로 안전 처리됨을 단언.
- 검증: 빈 rag_qa/recommend → 422(정상 복원), 위조 마커 → 503, 결정론 **181 유지**.

## 7. Codex 라운드5 (`reports/_codex_final_acceptance_review_r5.txt`) → 강화
R5 판정: **인수 보류** — (높음) 프로세스 전역 nonce가 재사용되고 마커가 stdout에 실려, 정상 응답 1건의
원시 stdio를 관찰하면 nonce 회수·재사용 가능. (중간) 비-AppError 메시지에 'validation error'가 우연히
섞이면 422로 오분류.
- **높음 → 호출별 1회용 nonce**: `_new_nonce()`를 `call_tool`마다 발급(각 호출이 이미 새 서브프로세스라
  자연스러움). 지난 호출의 nonce를 관찰·재사용해도 다음 호출은 다른 nonce라 위조 불가. (게다가 `_tool_error`가
  마커를 제거하고 반환하므로 nonce는 HTTP 응답에도 노출되지 않음.)
- **중간 → 휴리스틱 정밀화**: pydantic 인자 오류의 고유 시그니처 `\d+ validation error(s) for \w+Arguments`만
  422로 인정. 도구 내부 메시지에 'validation error'/'field required'가 섞여도 503 유지.
- 테스트: 호출별 nonce 마커 복원, 위조(무nonce/틀린nonce)→InfraError, 휴리스틱 정밀도(비-Arguments 'validation error'→503) 추가.
- 재검증: 결정론 **182 = CI 154 + mcp 8 + ml 20**. stdio: 빈 rag_qa→422, unknown→422, 위조→503.
