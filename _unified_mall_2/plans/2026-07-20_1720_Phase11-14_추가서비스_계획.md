## 결정된 구현 방식 (사용자 확인 완료)
- **화상 상담(3번)**: 웹캠(고객 얼굴 미리보기) + AI 아바타 패널(말할 때 움직이는 간단한
  아이콘 애니메이션, 실제 영상 생성 없음) + STT/TTS 음성 대화. VideoChat3 같은 영상이해
  모델은 검토했으나 이 프로젝트 규모·목표(RAG/LangChain/벡터DB 학습)에 비해 과도한 추가
  의존성(9GB 가중치, GPU 상주, trust_remote_code, 실시간 대화용이 아님)이라 **채택 안 함**
  — future-work로만 리포트에 기록.
- **얼굴 로그인 2차인증(5번)**: 실제 얼굴인식. 프론트는 가벼운 검출(미리보기)만 하고, 백엔드가
  실제 임베딩 추출/비교를 수행 — 사용자의 이전 프로젝트(`SKN32-2nd_GAJIMA_Dev`, insightface
  기반)와 같은 패턴을 따른다.

## Phase 11 — 음성 상담(STT/TTS)
- STT: `faster-whisper`(CTranslate2 기반, 로컬 실행, API 키 불필요) — 신규 의존성.
- TTS: `pyttsx3`(완전 오프라인, OS 내장 SAPI5 사용, 모델 다운로드·네트워크 불필요) — 신규
  의존성. 이 프로젝트가 지금까지 지켜온 "로컬 우선·무API키" 기조와 일치.
- 엔드포인트: `POST /api/voice/stt`(음성 파일 → 텍스트, 기존 `/api/agent/chat`으로 그대로
  전달 가능하게), `POST /api/voice/tts`(텍스트 → 음성 파일, 스트리밍 또는 파일 응답).
- UI: `index.html`(에이전트 채팅)에 마이크 버튼 추가 — 녹음 → STT → 기존 채팅 파이프라인 →
  응답 텍스트를 TTS로 재생하는 옵션 토글.
- 무폴백: STT/TTS 실패 시 명시적 에러(예: `InfraError`)로 알리고, 텍스트 채팅으로 조용히
  대체하지 않는다 — 사용자가 실패를 인지하고 텍스트 입력으로 직접 전환하게 한다.

## Phase 12 — 화상 상담 챗봇(아바타 패널)
- 신규 페이지 `video.html`: `getUserMedia`로 고객 웹캠을 좌측에 표시, 우측에 AI 아바타
  패널(CSS/SVG 애니메이션, TTS 재생 중에만 "말하는" 상태로 전환).
  Phase 11의 STT/TTS 엔드포인트를 재사용 — 별도 음성 파이프라인을 새로 만들지 않는다.
- 카메라 권한 거부 시: 텍스트 전용 모드로 안내(무폴백 — 조용히 카메라 없이 진행하지 않고
  "카메라 없이 텍스트로 계속하시겠습니까" 명시적 선택지 제공).

## Phase 13 — 얼굴 로그인 2차 인증
- 신규 의존성: `insightface`(+ `onnxruntime`, CPU) — 백엔드에서 얼굴 임베딩 추출·비교.
  (Codex 검토: InsightFace 제공 모델은 비상업 연구용 라이선스 — README에 명시.)
- DB: 별도 `FaceCredential` 테이블(embedding, user_id, created_at) — **opt-in**.
- **체인 잠김 방지(Codex 지적 반영)**: 얼굴 미등록 계정에 2차 인증을 강제하면 아무도 최초
  등록을 못 하는 순환 문제가 생긴다. 그래서 2차 인증은 **등록된 계정에만** 적용:
  - 얼굴 미등록 계정 → 기존 아이디/비번 로그인만으로 토큰 발급(기존 동작 그대로 유지).
  - 얼굴 등록 계정 → 비번 로그인 성공 후 얼굴 촬영 2차 인증까지 통과해야 최종 토큰 발급.
  - 등록은 반드시 **이미 로그인된 세션**에서만 가능(마이페이지) — 미인증 상태에서 얼굴만으로
    등록/로그인하는 경로는 없음.
- 보안 한계 문서화(Codex 지적 반영, 과장 금지): 이 구현은 **라이브니스(위조 방지) 검사가
  없다** — 인쇄된 사진·화면 재촬영에 취약할 수 있음을 README/리포트에 명시. 임베딩은
  원본 사진을 저장하지 않고 벡터만 저장, 실패 시도 횟수 제한(예: 5회) 적용. "포트폴리오/학습용
  구현이며 프로덕션 생체인증 보안 기준은 아님"을 명시.

## Phase 14 — 관리자 대시보드 요약보고서 생성/저장/인쇄
- 저장: 신규 의존성 `reportlab`(Windows에서 시스템 의존성 없이 설치 가능 — WeasyPrint는
  Cairo/Pango 네이티브 빌드가 필요해 이 환경엔 부적합해 제외) — `GET /api/admin/report`가
  현재 대시보드 데이터(준비상태·주문·이벤트·지식갭 요약)로 PDF를 생성해 `reports/`(또는 별도
  `generated_reports/`) 아래 저장하고 다운로드 응답을 반환.
- 인쇄: `admin.html`에 "인쇄" 버튼 — 브라우저 인쇄용 CSS(`@media print`)를 추가해
  `window.print()`로 즉시 인쇄 가능한 레이아웃 제공(별도 PDF 렌더링 없이 브라우저 네이티브
  인쇄 기능 사용 — 추가 의존성 없음).
- RBAC: 기존 `require_admin`으로 보호(신규 예외 없음).

## 순서·검증 방식(기존 관례 유지)
Phase 11 → 12 → 13 → 14 순서로 진행. 각 Phase마다: 계획 세부화 → Codex CLI 짧은 컨설트 →
구현 → **실 브라우저로 화면 직접 확인**(이 세션에서 이미 한 번 지적받은 "화면 안 열어봄" 실수
재발 방지) → pytest 회귀 → 리포트 작성 → history 기록 → 커밋.

## 리스크·미해결 사항 (사전 고지)
- STT/TTS/얼굴인식 모두 신규 무거운 의존성(faster-whisper, pyttsx3, insightface,
  onnxruntime, reportlab) 추가 — 설치·모델 다운로드 용량 확인 필요, 특히 첫 실행 시 모델
  가중치 다운로드가 발생할 수 있음(그 경우 명시적으로 알림, 조용히 실패하지 않음).
- pyttsx3는 Windows SAPI5 음성 엔진에 의존 — 로컬 환경에 설치된 음성팩 품질에 따라 발음
  품질이 달라질 수 있음(문서화할 한계).
- insightface 임계값(코사인 유사도 등) 튜닝은 실측 필요 — 초기값은 논문·라이브러리 기본값을
  쓰고 리포트에 근거를 남긴다.
